## Що вміє бекенд (перевірено на живому API)

| Ендпоінт              | Тіло                  | Відповідь                                                               |
| --------------------- | --------------------- | ----------------------------------------------------------------------- |
| `POST /auth/register` | `{ email, password }` | 400 — помилка валідації (поля, яких API не знає, теж дають 400)         |
| `POST /auth/login`    | `{ email, password }` | 401 `{ message: 'Invalid credentials' }`, якщо логін або пароль невірні |
| `GET /auth/me`        | —                     | поточний користувач; 401, якщо не залогінений                           |
| `POST /auth/refresh`  | —                     | оновлює сесію з cookie; 401, якщо cookie немає                          |
| `POST /auth/logout`   | —                     | 204, очищає cookie                                                      |

- **Сесія зберігається в cookie.** Сервер ставить `accessToken`, `refreshToken` і `sessionId` з
  прапорами `httpOnly; Secure; SameSite=None`.
- **Фронтенд не бачить токенів і не зберігає їх** (ні в localStorage, ні в state). Браузер сам додає
  cookie до кожного запиту, бо в `apiClient` стоїть `withCredentials: true`.
- **CORS для `http://localhost:5173` з credentials уже дозволений.**
- **`GET /movies` і `GET /movies/:id` публічні.** А `POST`, `PATCH` і `DELETE /movies` без сесії
  повертають 401 `Missing session credentials`. Бекенд уже захищає зміни, тож фронтенд лише ховає
  кнопки, яких гість не може використати.
- Успішні `register`, `login` і `me` повертають
  `{ user: { _id, email, username, createdAt, updatedAt } }`.

## Правила доступу (бізнес-логіка)

| Хто         | Бачить список фільмів | Create / Edit / Delete                                         | `/login`, `/register`     |
| ----------- | --------------------- | -------------------------------------------------------------- | ------------------------- |
| Гість       | ✅                    | ❌ кнопок немає, замість них «Увійдіть, щоб керувати фільмами» | ✅                        |
| Залогінений | ✅                    | ✅                                                             | ❌ перенаправлення на `/` |

Сторінка `/` **публічна**: на неї не ставимо `PrivateRoute`.

## Крок 1. Типи та валідація

- [ ] `src/validation/authSchema.ts`: Yup-схеми `loginSchema` і `registerSchema`. У реєстрації

**Що перевіряю:** типи відповідають реальному API; повідомлення валідації зрозумілі.

## Крок 9. Перехоплювач 401 і оновлення сесії

- [ ] В `apiClient.ts` додати response interceptor:
  1. Якщо прийшов 401 і запит ще не повторювали (прапор `_retry`) і це не `/auth/*`, викликати
     `POST /auth/refresh` і повторити початковий запит.
  2. Якщо одночасно прийшло кілька 401, `refresh` має виконатися **один раз**. Для цього зберігаємо
     спільний `Promise` оновлення.
  3. Якщо `refresh` повернув 401, викликати зареєстрований колбек `onSessionExpired`. Його реєструє
     `AuthProvider` через `useEffect`, і колбек ставить `['auth','me']` у `null`. Кнопки керування
     зникнуть самі, а `PrivateRoute` перекине з приватних сторінок на `/login`.
  4. Мутація, що впала з 401, показує «Session expired, please log in again», а не загальну помилку.

**Що перевіряю:** немає нескінченного циклу запитів; кілька паралельних 401 дають один `refresh`.
Тест: видалити cookie `accessToken` у DevTools і перезавантажити сторінку.
